# Технические требования к генерации step JSON (для ИИ)

Документ описывает **формат и правила текстовых полей** в `steps.json` и связанных JSON (discovery), а также рекомендации по балансу контента. Смысловые и языковые нюансы обсуждаются с бизнесом/лингвистом; здесь — то, что нужно для корректной работы парсеров, Speaker, игр и UI, плюс методический каркас для масштабирования.

---

## 0. Рекомендации по структуре урока (методология)

Чтобы избежать «каши» и повторов при масштабировании контента:

**Золотая пропорция шага:**
- **~80%** — активный кирпич: `word`, `phrase` (то, что собирается в Recall и произносится в Speaker).
- **~20%** — контекстный клей: `tip`, `casual`, `dialog` (объясняет, зачем и как это говорить).

**Scaffolding (леса) — рекомендуемая последовательность в уроке:**
1. **word** — базовый кирпич (напр. «Остро»).
2. **word** — направление/следующий кирпич (напр. «Мало»).
3. **phrase** — сборка (напр. «Сделайте мало остро»).
4. **tip** — культурный код (почему «мало остро» для тайца всё равно «пожар»).

Не строить уроки «просто словами»: чередовать кирпичи и контекст. ИИ при генерации должен соблюдать эту логику.

## 1. Файлы и структура

| Файл | Назначение |
|------|------------|
| `steps.json` | Степы по урокам: корневой объект `{ "version": number, "stepsets": StepSet[] }` |
| `lessons.json` | Метаданные уроков; поле `links.steps_ref` должно совпадать с `StepSet.id` |
| `taika_basa_course.json` | Метаданные курсов (без степов) |

**StepSet:**

- `id` (string) — уникальный идентификатор набора, например `"course_b_1_l1_steps"`.
- `course_id` (string) — идентификатор курса.
- `lesson_id` (string) — идентификатор урока; должен совпадать с `lesson_id` в `lessons.json`.
- `hints` (array of string, опционально) — подсказки урока.
- `tags` (array of string, опционально) — темы урока для дедупликации и поиска, напр. `["food", "market", "spicy"]`. Позволяет ИИ при генерации новых уроков проверять, не создаётся ли дубликат (напр. слово «остро» в пятый раз). В текущей модели кода поля нет — при добавлении в JSON декодер его проигнорирует, пока в `StepSet` не будет объявлено свойство `tags`.
- `items` (array of StepItem) — список степов.

**Важно:** порядок степов в UI определяется полем `order` у каждого элемента, а не порядком в массиве. Массив обычно уже отсортирован по `order` для читаемости.

## 2. StepItem: обязательные и опциональные поля

Модель в коде: `StepItem` (см. `StepData.swift`).

### 2.1 Обязательные для всех

| Поле | Тип | Правило |
|------|-----|--------|
| `order` | number | Уникальный в рамках одного stepset. Целое, от 1. Определяет порядок показа. |
| `kind` | string | Один из: `"word"`, `"phrase"`, `"casual"`, `"tip"`, `"dialog"`. Регистр строго lowercase. |

### 2.2 Поля по `kind`

**word, phrase, casual (обучаемые степы):**

| Поле | Тип | Обязательность | Описание |
|------|-----|---------------|----------|
| `ru` | string | да | Перевод/значение на русском. |
| `thai` | string | да | Текст на тайском (оригинал). |
| `phonetic` | string | **да** для учёта в прогрессе | Транскрипция кириллицей (см. раздел 3). Без него степ не считается для прогресса и Speaker. |
| `tip` | string | нет | Подсказка для пользователя. |
| `audio` | string | нет | Имя/путь к аудиофайлу. |

**tip (лайфхак/подсказка):**

| Поле | Тип | Обязательность |
|------|-----|----------------|
| `text` | string | да (или `tip`) |
| `tip` | string | альтернатива к `text`; в коде приоритет у `text`. |

**dialog (диалог):**

| Поле | Тип | Описание |
|------|-----|----------|
| `scene` | string | опционально |
| `lines` | array of DialogLine | реплики; каждая: `who`, `ru`, опционально `th`, `phonetic`, `audio`. |

В текущем `steps.json` диалогов нет; структура поддерживается декодером.

### 2.3 Устранение дублирования: не использовать `type`

Поле `type` («Фраза», «Слово», «Лайфхак», «Неформально») в текущем JSON дублирует `kind`. Рекомендация:

- **В новом и ревизуемом контенте не включать `type`.** Оставить только `kind`; отображение RU-названия типа вынести в код или в метаданные курса/локализацию. Это уменьшает размер JSON и убирает риск рассинхрона между `type` и `kind`.
- Если `type` уже есть в старом JSON — декодер его игнорирует (поля нет в модели). Удаление при рефакторе контента — по желанию.

**Прочие игнорируемые поля:** `id` у StepItem (локальный идентификатор степа) — в коде не используется. Добавление других произвольных полей допустимо: `JSONDecoder` по умолчанию не падает на неизвестные ключи.

## 3. Правила текстовых полей (критично для парсеров и Speaker)

### 3.1 Разделитель слогов в `phonetic`

- **Допустимые разделители слогов:** дефис-minus (ASCII) `-` (U+002D) или **пробел**, если у каждого слога указана стрелка тона (→↓↘↑↗). Парсеры (Speaker, steps_to_contours, Recall) разбивают по `[\s\-·]+`, поэтому оба варианта обрабатываются.
- **Рекомендация:** при наличии стрелок тонов использовать пробел между слогами: `са→ ват→ ди↘` вместо `са→-ват→-ди↘` — дефисы избыточны.
- **Без пробелов вокруг дефиса**, если используется дефис: не `слог - слог - слог`.
- **Запрещено:** en-dash `‑` (U+2011), em-dash `—`, minus sign `−`.

**Примеры корректно:**  
`"phonetic": "са-ват-ди↘"` (дефисы);  
`"phonetic": "са→ ват→ ди↘"` (пробелы при стрелках тонов).

**Рекомендация для ИИ:** после генерации транскрипции заменить все варианты дефиса/минуса между слогами на один символ `-` (U+002D) и не вставлять пробелы вокруг дефиса.

**Известная проблема в текущем steps.json:** в части записей используется Unicode en-dash `‑` (U+2011) вместо ASCII `-`. Такие фразы в Speaker/играх разбиваются по слогам некорректно. При генерации новых степов и при ревизии контента использовать только ASCII hyphen-minus.

### 3.2 Тоновая нотация в `phonetic`

Speaker API и Recall Game полностью зависят от единообразного формата транскрипции. В текущем steps.json нотация местами плавает (стрелочки и дефисы вперемешку). Строгие правила для ИИ:

- **Стрелки тонов** (↗, ↘, →, ↑, ↓) — допустимы и рекомендуются. Они должны стоять **после слога**, не перед ним и не в середине. Для работы Speaker и tone API у **каждого** слога должен быть ровно один из пяти тонов.
- **Один способ маркировки на запись:** если используешь стрелки тонов, **не дублируй** ударение combining acute (`́`). Иначе парсеры и ИИ путаются.
  - **Хорошо:** `са→-ват→-ди↘` (каждый слог с тоном); допустимо и `са-ват-ди↘` (тон только на последнем, остальные по умолчанию Mid).
  - **Плохо:** `са-ват-ди́↘` (стрелка + ударение на одной позиции — избыточно и мешает автоматике).
- Допустимые символы тона (все пять используются в Speaker/tone API):
  - `→` — ровный (Mid);
  - `↘` — падающий (Falling);
  - `↗` — восходящий (Rising);
  - `↑` — высокий (High);
  - `↓` — низкий (Low).
- При желании можно использовать только ударение `́` без стрелок (для слов без контраста тонов); но **не смешивать** стрелки и ударение на одном и том же слоге в одной строке.
- Разделитель слогов — только `-`; тоновые символы не являются разделителями.

### 3.3 Пробелы и переносы

- В коде все строковые поля при использовании обрезаются по краям: `trimmingCharacters(in: .whitespacesAndNewlines)`.
- **Рекомендация:** не оставлять ведущих и завершающих пробелов/переносов в полях `ru`, `thai`, `phonetic`, `tip`, `text` — это упрощает диффы и предсказуемость.
- Внутри строки пробелы допустимы (например, между словами в `ru` или между слогами в старом стиле); для разбора слогов важен только дефис `-` в `phonetic`.

### 3.4 Кавычки и экранирование в JSON

- В JSON все строки в двойных кавычках `"..."`.
- Экранировать: `"` → `\"`, `\` → `\\`, перевод строки → `\n`, табуляция → `\t`.
- В тексте на русском/тайском/транскрипции лучше избегать неэкранированных переводов строк внутри одного поля (один логический абзац — одна строка), иначе JSON и отображение усложняются.

### 3.5 Длина и кодировка

- Кодировка файла: **UTF-8**.
- Ограничения по длине в коде не заданы; ориентиры по размеру и «чистоте» контента — в разделе 4.

## 4. Размер и чистота контента карточки

Чтобы карточки не перегружали пользователя и корректно отображались в UI, Recall и Speaker, ИИ при генерации должен соблюдать следующие правила.

### 4.1 Размер

- **Одна карточка — одна мысль.** Не объединять несколько разных фраз или вариантов в один степ «для экономии».
- **`ru` (перевод/значение):** коротко. Рекомендуемый ориентир — до **~60 символов** для комфортного отображения в карточках и играх (напр. MatchGame). Слишком длинные фразы на русском утяжеляют карточку и плохо читаются на мобильном.
- **`phrase` по смыслу:** не длинная тирада. Фраза должна быть произносимой и запоминаемой; если по сути это два предложения — лучше разбить на два степа или упростить.
- **`phonetic`:** для RecallGame в коде рекомендуется не более **~6 слогов** на фразу; степы с большим числом слогов могут исключаться из Recall. При генерации длинных фраз это стоит учитывать.
- **`tip` / `text`:** могут быть длиннее, чем `ru`, но лучше одна законченная мысль, без «и ещё вот это, и вот это».

### 4.2 Чистота русского текста: без скобок и слэшей-мусора

- **Не утяжелять `ru` скобками и слэшами.** Фразы вида «Фраза (вариант для мужчин) / (для женщин)» или «Остро (про еду) / (про перец)» создают визуальный шум и ощущение «крапа» в каждой карточке. Пользователь должен сразу видеть одно ясное значение.
- **Правило:** если есть два разных варианта перевода или контекста — выбрать **один** основной и записать его коротко, без скобок и « / ». Либо оформить варианты отдельными карточками (разные `order`).
- **Допустимо** в исключительных случаях одна короткая уточняющая скобка, если без неё смысл теряется (напр. «Счёт (в ресторане)»), но не делать скобки и слэши правилом в каждой карточке.

### 4.3 Без лишних сокращений и «воды»

- В полях `ru`, `tip`, `text` **не использовать** сокращения-заполнители: «и т.д.», «и т.п.», «и др.» в каждой карточке. Они не несут пользы в одном шаге и засоряют контент. Либо написать конкретику, либо опустить.
- Избегать канцелярита и длинных пояснений в `ru`: карточка — не энциклопедия, а один кирпич для запоминания.

### 4.4 Краткая памятка для ИИ

| Что | Как |
|-----|-----|
| Длина `ru` | До ~60 символов, одна мысль. |
| Фраза | Не тирада, произносимо и запоминаемо. |
| Скобки и слэши в `ru` | Не делать нормой; один вариант на карточку. |
| Сокращения (и т.д., и т.п.) | Не использовать. |
| Слогов в `phonetic` | Для Recall удобно до ~6; длинные фразы — с осторожностью. |

## 5. Связь с lessons.json

- В уроке в `links.steps_ref` указывается строка, равная `StepSet.id` из `steps.json` (например `"course_b_1_l1_steps"`).
- Поле `preview_phrase` в уроке (если есть) задаётся в формате:  
  `"русский текст;транскрипция с дефисами"`  
  разделитель — точка с запятой `;`. Транскрипция должна использовать тот же стандарт дефисов, что и `phonetic` в степах.

---

## 6. Валидация, которую выполняет приложение

- **Прогресс и Speaker:** для `kind in ["word", "phrase", "casual"]` степ считается пригодным для прогресса и спикера только если `phonetic` после trim не пустой (`StepData.isValidForProgress`).
- **RecallGame:** разбиение по слогам делается по `phonetic.split(separator: "-")`; если в `phonetic` использованы другие разделители, слоги будут определены неверно.
- Дубликаты `order` внутри одного stepset не проверяются явно; дубликаты приводят к неочевидному порядку — лучше гарантировать уникальность на этапе генерации.

## 7. Чек-лист для ИИ при генерации step JSON

1. **Корень:** `version` (число), `stepsets` (массив).
2. **StepSet:** для каждого набора заданы `id`, `course_id`, `lesson_id`, `items`; при необходимости `hints`, при необходимости `tags` (массив тегов для дедупликации).
3. **StepItem:** у каждого есть `order` (уникальный в stepset) и `kind` (строго один из: `word`, `phrase`, `casual`, `tip`, `dialog`).
4. **word/phrase/casual:** заполнены `ru`, `thai`, `phonetic`; в `phonetic`: разделитель слогов **только** ASCII `-` (U+002D), без пробелов вокруг; при использовании стрелок тонов (↗↘→) не дублировать ударение (`́`) на том же слоге.
5. **tip:** заполнено `text` (или `tip`).
6. **dialog:** при наличии — `lines` с полями по контракту `DialogLine`.
7. Поля `ru`, `thai`, `phonetic`, `tip`, `text` без ведущих/концевых пробелов и без лишних переносов внутри.
8. JSON валиден (кавычки, запятые, скобки); файл в UTF-8.
9. Идентификаторы `steps_ref` в `lessons.json` совпадают с `StepSet.id` в `steps.json`.
10. В новых степах не включать поле `type` (достаточно `kind`).
11. Баланс урока: ~80% word/phrase, ~20% tip/casual/dialog; последовательность по принципу Scaffolding (word → word → phrase → tip).
12. Размер и чистота: `ru` до ~60 символов, одна мысль; без скобок/слэшей в каждой карточке; без «и т.д.»/«и т.п.»; фраза не тирада.

## 8. Резюме для ИИ (три блока)

| Блок | Правило |
|------|--------|
| **Методология** | Золотая пропорция 80/20 (кирпич vs клей). Scaffolding: word → word → phrase → tip. Не уроки «просто словами». |
| **JSON** | Только `kind`, без дублирующего `type`. Опционально `tags` у StepSet для дедупликации. |
| **phonetic** | Разделитель только `-`, без пробелов вокруг. Стрелки тонов (↗↘→) после слога; не смешивать со знаком ударения `́` в одном слоге. |
| **размер и чистота** | `ru` коротко (~60 символов), одна мысль. Без скобок и слэшей в каждой карточке; без «и т.д.»/«и т.п.»; фраза не тирада; один вариант на карточку. |
