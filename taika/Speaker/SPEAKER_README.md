## 4. STATE MACHINE

Speaker имеет строгое состояние:

idle
recording
analyzing
result
error

Transitions строго контролируются SpeakerManager.

Запрещено:
- менять состояние из View
- обновлять ObservableObject во время рендера
- выполнять publish внутри body

State machine должна быть детерминированной и тестируемой.

Дополнительное требование:
- состояние analyzing НЕ может переходить в recording напрямую
- состояние result НЕ может публиковать новое состояние во время body-render
- любые publish должны происходить через main actor dispatch после завершения async операций

Это предотвращает:
- "Publishing changes from within view updates"
- race conditions
- двойной analyze-вызов

Никаких side effects внутри View.

Все transitions происходят внутри SpeakerManager.

### 5.1 Как считается скор (обычный режим до разбора)

В режиме практики по карточкам скор выставляется **без Azure**, целиком на устройстве:

1. **Запись** — микрофон пишет в файл (SpeakerRecorder), по стопу вызывается анализ.
2. **Распознавание** — Apple **SFSpeechRecognizer (th-TH)** по файлу возвращает тайский текст того, что сказал пользователь (`spoken`). Он-device или облако Apple, в проде то же самое.
3. **Эталон** — тайский текст шага из контента: `cur.face.subtitleTH` (`expectedThai`).
4. **Сравнение** — по **тайскому тексту**, не по кириллице:
   - обе строки нормализуются: `normalizeThai()` убирает пробелы, пунктуацию, лишние символы;
   - считается расстояние Левенштейна между нормализованными строками;
   - **similarity** = `1 - (levenshtein / max(lengths))`, значение от 0 до 1;
   - **score** = `Int((similarity * 100).rounded())` — целое 0…100.
5. **Подсказка (hint)** — по диапазону скора:
   - 92…100 → «очень похоже. попробуй быстрее и слитно»;
   - 78…91 → «норм. добей окончания и тон»;
   - 60…77 → «слышно похоже, но есть ошибки. сравни по слогам»;
   - иначе → «пока мимо. включи эталон и повторяй по 1–2 слога».
6. **В UI** в блоке результата «ты сказал» показывается эталонный **phonetic** (кириллическая транскрипция по слогам из StepData), а не сырой вывод ASR — чтобы пользователь видел читаемую форму; сравнение и скор при этом считаются по тайскому (spoken vs expectedThai).

Код: `SpeakerManager.stopAttemptAndAnalyze()` → `recognizeThai(url:)` → `similarity(a: spoken, b: expectedThai)` → `feedbackHint(for: score)`; детальный разбор по слогам/тонам (PRO) пока заглушка, реальная оценка тонов будет подключена отдельно.

### 5.1.1 Одна общая оценка (спикер и разбор)

Чтобы не было расхождения «на карточке 100, в разборе 30» или «на карточке 0, в разборе 70», везде показывается **одно число** — `displayScore`:

- **Без разбора по тонам:** общая оценка = скор по тексту (ASR vs эталон), как раньше.
- **С разбором по тонам:** общая оценка = min(скор по тексту, средний тон по слогам). То есть оба аспекта должны быть хороши, число одно и на карточке, и в шапке разбора.

В модалке «разбор» под общей оценкой выводится расшифровка: «Текст X% · Тон Y%. Ниже — по слогам.» — так пользователь видит, из чего сложилось одно число.

### 5.2 Разбор по тонам (эталон, ограничения, что делать дальше)

**Когда есть эталон по записи**

- Эталонный график тона в карточке «разбор» строится **только по ответу API** разбора по тонам.
- API вызывается при нажатии «Разбор» (PRO): отправляются запись пользователя, тайский текст шага и при наличии — `expected_tones` из поля `phonetic` шага (стрелки ↘→↗ и т.д.).
- Ответ API содержит по каждому слогу: `tone_expected`, `tone_actual`, оценка, фидбек. Из этих данных на клиенте собирается и эталонная линия (по `tone_expected`), и линия «Ты сказал» (по реальному контуру из API).
- **Итог:** эталон показывается **по всем записям, по которым успешно получен разбор по тонам** (есть ответ API с массивом слогов). Если API не вызывался или вернул пустой/ошибочный ответ — блок «График тона по фразе» либо не показывается, либо показывается без эталонной линии.

**Текущие ограничения**

1. **Бэкенд разбора по тонам** — только локально (Mac, `scripts/thai_tone_assessment`, `./start_api.sh`). В проде `toneAssessmentBaseURL == nil`, API не вызывается, разбор по тонам и эталонный график недоступны.
2. **Эталон — синтетический:** линия «Эталон» рисуется по шаблону (Mid/Low/High/Falling/Rising) из ответа API, а не по реальному аудио эталона. Реальные контуры из WAV эталонов можно генерировать скриптом `steps_to_contours.py` (режим `--audio-dir`), но в приложении пока не используются.
3. **Прогресс прорисовки эталона:** при воспроизведении TTS эталона линия рисуется синхронно с аудио (0…1). При открытии карточки разбора прогресс сбрасывается в 1.0, чтобы эталонная линия была видна целиком.
4. **Слоги:** разбиение на слоги и тоны делается на бэкенде (PyThaiNLP + правила). Если в контенте нет `phonetic` со стрелками — в запрос уходит `expected_tones` по умолчанию (все Mid), эталон будет «плоским».

**Что делать дальше**

- **Прод:** поднять HTTPS-сервис разбора по тонам, выставить URL в приложении (или через конфиг), чтобы разбор и эталон работали для всех пользователей.
- **Контент:** заполнять `phonetic` в шагах (стрелки тонов по слогам), чтобы эталон и оценки по слогам были осмысленными.
- **Эталон из аудио (опционально):** подключить предвычисленные контуры из `steps_to_contours.py` (или аналог) в бэкенд/приложение, чтобы линия «Эталон» отражала реальное произношение из эталонного WAV.

## 6. PROGRESS & MASTERY INTEGRATION

Speaker — это Production Layer в Mastery Model.

Он НЕ:
- завершает Step
- обновляет completion
- влияет на exposure

Он обновляет только production-метрики.

### 6.1 What Speaker Updates

SpeakerManager передает в ProgressManager:

- bestPronunciationScore
- rollingAverageScore (последние N попыток)
- productionAttempts
- lastAttemptDate

Speaker НЕ считает masteryScore.

MasteryScore пересчитывается ТОЛЬКО внутри ProgressManager.

### 6.2 Mastery Formula Contract

Production contribution:

productionScore = normalizedRollingAverage

Где:

normalizedRollingAverage =
    average(last 3 attempts)
    ИЛИ
    average(best 3 attempts из последних 5)

Требование:
- минимум 3 попытки для расчета
- 3 подряд успешных попытки (> threshold) повышают confidenceLevel
- один случайный высокий score НЕ считается mastery

ConfidenceLevel используется ProgressManager для расчета masteryLevel.

### 6.3 Mastery Threshold Impact

Speaker влияет на:

- masteryScore
- masteryLevel (New → Learning → Stable)

Но НЕ блокирует переход к следующему Lesson.

Если mastery < threshold:
- LessonsView показывает soft warning
- контент НЕ блокируется

### 6.4 Persistence & Recovery

Все production-данные сохраняются через UserSession.

При:
- перезапуске приложения
- reinstall
- device migration

ProgressManager должен восстановить:
- productionAttempts
- rollingAverageScore
- masteryLevel

Speaker НЕ хранит данные локально как single source of truth.

---

### 6.5 Mastery Decay Integration

Speaker участвует в механике Mastery Decay.

Если Step переходит из Stable → Learning из-за decay:

- Speaker НЕ сбрасывает bestPronunciationScore
- Speaker НЕ удаляет историю попыток
- decay влияет только на masteryScore внутри ProgressManager

Decay-triggered события:
- LessonsView может показывать soft warning
- Main может инициировать возврат в Step
- возможно future push notification (Mastery Recovery Loop)

SpeakerManager не рассчитывает decay.
Decay живет только в ProgressManager.

### 6.6 Хранение попыток и продакшен

- **Попытки:** метаданные (courseId, lessonId, stepIndex, score, attemptCount) — UserDefaults; аудиофайлы — каталог `Application Support/SpeakerRecordings/` (не Caches), чтобы iOS не удалял их.
- **Прод:** отдельная база/бэкенд для Speaker не нужна. Распознавание — Apple SFSpeechRecognizer (on-device или облако Apple для тайского). В проде работает так же, как в разработке.
- **Ошибка 1107 (kAFAssistantErrorDomain):** «распознавание недоступно» — часто из‑за: нет сети/квоты при server-side, тайский не загружен для Диктовки (Настройки → Основные → Клавиатура → Диктовка → Тайский), нехватка памяти на устройстве. При 1107 попытка сохраняется с оценкой 0, запись копируется в Application Support — пользователь может послушать запись и повторить позже.

**Как это работает в проде на каждом устройстве**

- **Новая установка** (пользователь впервые скачал приложение): хранилище пустое. Все попытки после установки пишутся в UserDefaults + файлы в Application Support. Воспроизведение записей работает.
- **Обновление с прошлой версии:** в UserDefaults могут остаться старые попытки, у которых путь к файлу указывал в Caches (или временный путь). iOS мог уже удалить эти файлы. При открытии такой карточки: скор и счётчик попыток восстанавливаются из UserDefaults, но файл по старому пути не находится → кнопка «моя запись» неактивна, в экране результата показывается подпись «запись недоступна». Все **новые** записи (после обновления) сохраняются в Application Support — у них воспроизведение есть.
- **Итог по «старым записям»:** под старыми имеются попытки, сохранённые до переноса файлов в Application Support. По ним остаётся только скор (и текст подсказки), воспроизведение недоступно; в UI явно показывается «запись недоступна». Никакой миграции старых файлов нет (их уже может не быть на устройстве). Синхронизации между устройствами нет — каждое устройство хранит только свои попытки локально.

## 12. QUEUE SOURCES AND FILTERS (EPIC 3)

Откуда берутся карточки в спикере:

- **baseQueue** (при открытии и для режима «случайные»): строится в `rebuildQueue()` из `UserSession.snapshot.learnedSteps` (выученные шаги). Если выученных нет — очередь пустая (daily picks убраны в EPIC 3).
- **Текущий урок**: все шаги **последнего открытого урока** (lastCourseId, lastLessonByCourse), для которых есть контент спикера. Очередь строится по реальному списку шагов урока (`StepData.items(for: lessonId)`), а не по скану индексов — поэтому не теряются шаги из конца урока. В очередь попадают только шаги с `kind == word/phrase/casual` и непустые `titleRU` + `subtitleTH` (остальные — советы, диалоги, пустые — не показываются). Поэтому «много карточек в уроке» в UI может дать меньше карточек в Спикере: считаются только «озвучиваемые» шаги.
- **Избранное**: id из `FavoriteManager.speakerStepIds()`; резолв через StepData с учётом case-insensitive lessonId (нормализация FM vs ключи в steps.json).
- **Выученные**: только шаги из learnedSteps. Если выученных нет — пустая очередь и подсказка «пока нет выученных фраз».
- **Случайные**: baseQueue в случайном порядке.

**Почему в «текущем уроке» две карточки после первого урока:** в первом уроке два шага с контентом для спикера; оба попали в последний открытый урок. Это ожидаемое поведение, не заглушки. Логика не сбилась.

Разбор по слогам на экране результата отключён до появления реального провайдера (Azure). Сейчас показываются только общий скор и текстовая подсказка (hint).

**Пустые очереди (EPIC 3):** заглушки daily picks («са ват ди» и т.п.) убраны. Если выученных шагов нет, baseQueue пустой; для каждого фильтра показывается сценарий пустого состояния: «в избранном пусто», «пока нет выученных фраз», «пройдите урок — здесь появятся фразы для тренировки» и т.д.

**«Получить разбор» и PRO:** кнопка «получить разбор» синхронизирована с ProManager и OverlayPresenter. Если пользователь PRO (`can(.speakerAdvanced)`), открывается модалка разбора (сравнение «ты сказал» / «нужно было» + подсказка). Если не PRO, показывается paywall (Overlay.speakerPaywall → PROView с initialPage для спикера) — сквозной процесс завлечения на покупку PRO. Paywall рендерится на уровне AppShell, чтобы открываться с любой вкладки (в т.ч. со вкладки Спикер).

## 12.1. STEP–SPEAKER USER FLOW (клиентский путь)

**Цель:** связать прохождение урока (Step) и закрепление произношением (Speaker) в один понятный путь.

**Текущее поведение:** после завершения урока показывается summary overlay: «Закрепить урок» (игры: Найди пару, Быстрое повторение, Фразы в контексте) и кнопка «Следующий урок». Пользователь может вручную перейти во вкладку Спикер; фильтр «текущий урок» уже показывает карточки последнего урока.

**Рекомендуемое улучшение:** в summary overlay после урока добавить явный CTA «Потренировать произношение» (или «Закрепить в Спикере»), который переключает на вкладку Спикер с фильтром «текущий урок». Так закрепление произношением становится частью пост-урока наравне с играми и следующим уроком. Реализация: NavigationIntent.requestTab(2) + закрытие overlay / popToRoot; при открытии Спикер уже подставляет «текущий урок» по lastCourseId/lastLessonByCourse.

## 12.2. NAVIGATION & FILTERING AT SCALE (EPIC 3 продолжение)

Когда уроков/карточек мало (1 → 2 → 3) — одного уровня фильтров достаточно. Когда уроков 10–20+, пользователю нужна ясность: **какой урок** имеется в виду и **откуда карточка**.

**План улучшений:**

1. **«Последний урок» вместо «текущий урок»**  
   Название фильтра: «последний урок» (последний пройденный/открытый). В пилле фильтра уже показывать **название урока** (subtitle) — источник данных: lastCourseId/lastLessonByCourse + LessonsData.lessonTitle / displayLessonTitle. Так пользователь сразу видит, например: «последний урок · Урок 3».

2. **Чип на карточке**  
   На каждой карточке Спикера — небольшой чип с названием урока (как в Избранном: lessonTitle в капсуле). Данные уже есть: SpeakerItem.lessonTitle, заполняется из lessonTitleForLessonId(cur.lessonId). При 10–20 карточках из разных уроков сразу видно, из какого урока фраза.

3. **Второй уровень фильтра для «выученные»** (реализовано)  
   В режиме «выученные» под основной полоской фильтров показывается вторая: «Все» | «Урок 1» | «Урок 2» | … (по списку уроков, в которых есть выученные шаги). SpeakerManager: `learnedLessonIds`, `learnedLessonFilter`, `setLearnedLessonFilter(lessonId)`; при выборе урока очередь фильтруется по lessonId. Отступы полосок приведены к PD.Spacing.screen (единая сетка с остальным приложением).

**Унификация Step и Speaker:** общий компонент полоски фильтров (edge-to-edge, один стиль) и при необходимости фильтр по типу карточек в Step («все» | «слова» | «фразы» | «советы») — в бэклоге; при редизайне этой зоны можно вынести общий TaikaFilterStrip в Theme и использовать в обоих экранах.
